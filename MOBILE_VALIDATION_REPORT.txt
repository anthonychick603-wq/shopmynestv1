=== v1.0.190 — Approval alert routes to shop setup; one-tap alert rows ===

Bug: The "Your seller application was approved" alert on the Alerts
screen didn't feel tappable and its title was truncated. Sellers had
no obvious path from the approval alert into the flow that actually
finishes onboarding (name, tagline, about).

Root causes:
  1) The alert row was split into two Touchables — body tap marked
     read, a separate small pill labeled "Open" navigated. That pill
     was easy to miss and consumed enough width to truncate long
     titles.
  2) `rowTitle` had no `numberOfLines` cap so it either overflowed
     or clipped depending on width.
  3) The approved-application route pointed to /seller/dashboard,
     but the dashboard is not where a fresh seller sets up their shop
     — /seller/shop-settings is (owns store_name, tagline, about).

Fixes:

  app/(tabs)/(more)/alerts.tsx
    - Row is now a single TouchableOpacity: tapping ANYWHERE on it
      marks-as-read AND navigates in one gesture (inbox pattern).
    - Removed the separate "Open" pill button (dead code path,
      cleaner layout).
    - Added a decorative chevron on the right when a route exists,
      so the affordance is obvious.
    - `rowTitle` gets `numberOfLines={2}`, `rowBodyText` gets
      `numberOfLines={3}` — no more clipped titles.
    - `rowText` gets `minWidth: 0` so the flex child collapses
      properly next to the icon and chevron.

  src/hooks/use-notification-routing.ts
    - `seller_application_approved` / `seller_approved` /
      `application_approved` and any `seller_application_update`
      with status=approved now route to /seller/shop-settings
      instead of /seller/dashboard, so an approved seller lands
      directly on the shop-setup screen where they can enter their
      shop name, tagline, and about. Non-approved statuses still
      route back to /seller/apply.

Behaviour parity with push notifications:
  Push-tap and Alerts-row-tap share `routeForPush()` so the tapping
  experience is identical on both surfaces.

=== v1.0.188 — Ship-from address inputs above the keyboard ===

Bug fix: on the seller Ship-from address screen (and every other form
using KeyboardAwareScroll), the on-screen keyboard was still burying
the lower inputs — the wrapper's auto-scroll fired but under-scrolled
because of three separate races.

Root causes patched in src/components/KeyboardAwareScroll.tsx:

  1) On Android, `keyboardDidShow` fires AFTER the keyboard is already
     fully up, while our internal `paddingBottom` + spacer haven't
     laid out yet. Calling `scrollTo` in that same tick clamps to the
     stale (pre-expansion) contentSize and under-scrolls. Fix: on
     Android, wait TWO rAF frames after the keyboard event so the
     spacer commits before we measure and scroll.

  2) The subscription registered `keyboardDidShow` twice on Android
     (once as show, once as change) which caused double-fires and
     an intermittent race between the two scroll attempts. Fix: only
     register the change-frame listener on iOS where the event
     actually exists.

  3) The `scrollTo` fallback branch used `_lastContentOffsetY ? … : overlap`,
     which threw away the current offset when the user hadn't scrolled
     (offset = 0 is falsy) and forced the ScrollView to jump to a
     tiny absolute Y. Fix: use `?? 0` so a genuine top-of-form scroll
     position is preserved and we always add `overlap` to whatever the
     current offset is.

  4) The wrapper never re-scrolled when focus moved between fields
     while the keyboard was already up (tapping "next" on the
     keyboard, or tapping straight into another input). Fix: while
     the keyboard is visible, poll `TextInput.State.currentlyFocusedInput()`
     every 150ms; when the identity changes, re-scroll the new field
     above the keyboard.

Screen fix in app/(tabs)/(more)/seller/shippo.tsx:

  5) The Ship-from screen has a sticky header ABOVE the KeyboardAwareScroll
     wrapper, but the wrapper's `keyboardVerticalOffset` defaulted to 0.
     On iOS, `behavior="padding"` therefore undershot the shrink by
     exactly the header height (≈50pt), leaving the bottom inputs
     buried. Fix: pass `keyboardVerticalOffset={56}` on the shippo
     screen so iOS accounts for the header row.

Which surfaces benefit:
  - Seller > Ship-from address form (primary bug report).
  - Buyer > Address edit form (uses the same wrapper).
  - Seller > Product variations editor.
  - Any other screen using `<KeyboardAwareScroll>` inherits the four
    wrapper-level fixes automatically.

    needing a native single-select popover on Android.

    "All categories" mode when allowAll={true}.
  - src/components/MultiCategoryDropdown.tsx (new, 556 LOC).
    Multi-select primitive for browse. Same field/sheet frame, but
    each row is a checkbox toggle. Sub-category sheet groups options

  - src/components/CategorySubcategoryPicker.tsx (rewritten as shim).
